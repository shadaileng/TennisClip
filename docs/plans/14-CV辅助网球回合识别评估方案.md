## 一、背景与目标

### 1.1 背景

[01-需求分析与落地方案](./01-需求分析与落地方案.md) 确立了以 Step 3.7 Flash 多模态模型为核心的全链路（预处理 → 高光识别 → 剪辑 → 报告），其验收指标要求「高光回合识别准确率 ≥ 90%」。当前 highlight 节点依赖 LLM 全帧理解，存在三方面不足：

1. **时序定位粗糙**：LLM 输出的回合起止时间戳误差通常 ±1–2s，直接影响 15 秒集锦切取质量；
2. **训练场景特有干扰**：手机固定机位拍摄的训练视频常有多球同屏（球桶、备用球、地上死球），纯 LLM 易将静止死球误判为有效回合；
3. **成本与稳定性**：长视频抽帧调用多模态模型 token 成本高，且批量 100 条稳定性验收（AGENTS.md 指标）依赖链路低故障率。

公开资料（YOLOv8/v10/v11 网球检测 + DeepSORT/ByteTrack 追踪 + 事件状态机）表明，固定机位场景下 CV 前置切片可把回合边界精度提升到帧级，并显著降低 LLM 复核负担。

### 1.2 目标

本方案回答一个问题：**对 TennisClip 而言，引入「CV 前置切片 + LLM 语义复核」是否最优？如何量化评估？**

具体评估目标：

| 目标 | 说明 |
|------|------|
| G1 网球识别质量 | 单球检测召回/精度，遮挡与暗光下的鲁棒性 |
| G2 多球干扰排除 | 球桶/备用球/死球误入回合状态机的比例 |
| G3 球员识别 | 双人场景 A/B 身份区分与跨回合一致性 |
| G4 回合切分 | 起止时刻精度、击球计数、回合类型（发球/相持/失误）正确率 |
| G5 端到端融合 | CV 切片 + LLM 复核相对纯 LLM 的准确率增益与耗时/成本变化 |
| G6 工程可行性 | 算力（CPU/GPU）、内存、1–5 分钟视频 ≤ 30s（不含推理网络延迟）约束下的可行性 |

### 1.3 适用范围

- 输入：手机固定机位（网侧/看台侧）拍摄的 1–5 分钟训练/对打视频，720p/30fps（现有 preprocess 统一规格）；
- 场景：双人对打为主，允许教练旁观、球桶在画面内；
- 不适配：转播多机位剪辑视频、高速运动无固定机位的比赛录像。

## 二、评估方案设计

### 2.1 候选技术路线（来自公开调研）

| 路线 | 组成 | 公开参照 | 特点 |
|------|------|---------|------|
| R1 纯 LLM 抽帧（现状基线） | Step 3.7 Flash 抽帧 + prompts 约束输出时间戳 | 现有 highlight 节点 | 边界 ±1–2s；成本最高；Mock 可回退 |
| R2 事件状态机（CV 主路径） | YOLO 球/球员/击球检测 + ByteTrack/DeepSORT + 球场透视标定 + 击球/静止事件状态机 | Tennis-Analysis-System（92★）、Tennis-Vision（76★）、[2013 转播回合检测](https://doi.org/10.1080/19346182.2013.819007)、[2025 乒乓球记分牌回合检测](https://doi.org/10.1541/ieejeiss.145.1054) | 边界帧级；固定机位标定一次复用；需自建标注数据 |
| R3 视频模型兜底切片 | 微调 Video Swin 分类「有效回合片段」 | [xl-hacker/OnPoint](https://github.com/xl-hacker/OnPoint) | 无逐帧标注时低成本兜底；碎片切片需二次过滤 |
| R4 多模态 LLM 复核（辅） | CV 事件切片抽帧 + 结构化上下文注入 prompts/ | 现有 LLM 管线 | 语义复核（制胜/失误类型、胜者），Mock 降级为纯 CV |
| R5 球员 ReID 身份化 | 人体检测 + ReID 外观特征 + 登记制匹配 | [jananikolovska/tennis_player_detection](https://github.com/jananikolovska/tennis_player_detection) | 训练场景主角固定，登记制比通用 ReID 鲁棒 |

**推荐被评估主方案：R2 + R4（+ R5 可选），R1 作为基线，R3 作为降级兜底。**

### 2.2 核心规则定义（评估对象）

多球干扰排除（G2）与回合状态机（G4）的判定规则需先固化，作为评估基准：

1. **静止死球规则**：球轨迹连续 N ≈ 0.5s 速度 < 阈值 → 轨迹丢弃，永不参与回合；
2. **物理球径约束**：经球场透视变换 H 将球框投影到地面，换算「虚拟球径」落在 [10cm, 30cm] 区间才保留（近大远小）；
3. **活球判定**：球轨迹在球场投影内 + 速度突变点邻近球员球拍位置 + 与最近球员挥拍方向一致 → 激活为活球；
4. **回合状态机**：
   - 开始：发球/抛球事件（活球从静止转为抛物线）；
   - 进行中：击球事件 = 球速度 Δv 超阈值且突变点邻球拍区域，记录球员侧交替；
   - 结束：球落点出界 / 触网 / 双误 / 双方静止 ≥ 1.5s。
5. **输出**：`[t_start, t_end, 击球次数, 结束事件类型, 胜者侧]`。

### 2.3 指标体系

| 维度 | 指标 | 定义 | 目标（对齐 AGENTS.md 验收） |
|------|------|------|---------------------------|
| G1 网球识别 | AP / Recall@0.5 | 球框与 GT 球框 IoU≥0.5 判对 | AP ≥ 0.80（参照公开集成方案 0.863） |
| G1 网球识别 | 轨迹完整性 MOTA | 球轨迹与 GT 轨迹匹配率 | ≥ 0.85（遮挡中断后恢复率 ≥ 90%） |
| G2 干扰排除 | 死球误入率 | 静止球被状态机当作活球的回合数 / 回合总数 | = 0（硬指标） |
| G2 干扰排除 | 多球选球正确率 | 双球同屏时活球选择正确的回合占比 | ≥ 0.95 |
| G3 球员识别 | 身份混淆率 | 回合内 A/B 身份交换发生次数 / 回合数 | ≤ 0.05 |
| G4 回合切分 | 起止时刻精度 | 切分边界与 GT 误差 ≤ 1s（≤ 0.5s）的回合占比 | ≥ 0.90 / ≥ 0.70 |
| G4 回合切分 | 回合完整召回 | GT 回合被切出的比例（非碎片、非合并） | ≥ 0.90 |
| G4 回合切分 | 击球计数误差 | 平均 |均击球次数差| | ≤ 1 拍 |
| G5 融合增益 | 高光准确率提升 | R4 vs R1 的回合级准确率差 | +5pp 以上，且总准确率 ≥ 0.90 |
| G5 融合增益 | LLM token 下降 | 复核片段抽帧数 vs 全帧调用 | ≥ 50% |
| G6 工程 | 端到端耗时 | 1–5 分钟视频 CV 预处理（不含 LLM 网络延迟） | ≤ 30s |
| G6 工程 | 峰值内存 | CV 管线峰值 | CPU 模式 ≤ 4GB |

### 2.4 评测数据集（自建 + 公开）

| 数据 | 来源 | 用途 | 规模建议 |
|------|------|------|---------|
| D1 训练视频集 | 自有手机固定机位素材（含多球、暗光、遮挡子集） | 真实分布评测 | ≥ 30 条 / 每子集 ≥ 10 条 |
| D2 球检测标注 | Roboflow 开源网球数据集 + 自有补标（参照 [UTennis](https://github.com/YouruiGuo/UTennis) 事件标注范式） | 训练/微调 YOLOv8s（player/ball/strike 三分类） | 检测 ≥ 3k 张，标注回合级 GT ≥ 300 个 |
| D3 回合 GT 金标集 | 人工逐回合标注起止帧 + 击球计数 + 结束类型（参照 [OpenTTGames 扩展版](https://arxiv.org/abs/2512.19327) 逐帧球坐标 + bounce/net 事件范式） | G4/G5 金标评测 | ≥ 100 回合，覆盖发球/相持/失误/双误 |
| D4 公开基准（可选） | Tennis-Analysis-System 等仓库所用素材 | 交叉验证 | 少量 |

标注规范：回合 GT 使用 720p/30fps 帧号标注（与 preprocess 规格一致），每个回合记录 `start_frame, end_frame, strike_frames[], end_type, winner_side`。

### 2.5 对比评估矩阵

| 实验 | 配置 | 评估指标 | 结论判据 |
|------|------|---------|---------|
| E1 基线 | R1 纯 LLM（现有管线） | G4、G5、G6 | 产出基线数值 |
| E2 CV 主路径 | R2（YOLOv8s + ByteTrack + 状态机 + 静止/球径过滤） | G1–G4、G6 | G2 死球误入率 = 0 且 G4 完整召回 ≥ 0.90 才通过 |
| E3 融合 | R2 + R4（CV 切片 + LLM 复核注入 prompts/） | G5、G6 | G5 增益 ≥ +5pp 且 LLM token ↓ ≥ 50% 才值得上线 |
| E4 兜底 | R3 替代 R2（视频模型切片） | G4、G6 | 仅当 E2 训练数据不足时的降级评估 |
| E5 身份化 | E3 + R5（ReID 登记制） | G3 | 身份混淆率 ≤ 0.05 |

Mock 模式约束：E3/E4/E5 在 LLM Mock 模式下自动退化为纯 CV 结果（与现有 `llm.mock_mode: auto` 契约一致），评估报告需同时记录「真实模型」与「Mock」两组数据。

### 2.6 工程实现落点（与 AGENTS.md 契约对齐）

- 新增 `backend/services/cv_slice.py`（球场标定、球/球员检测追踪、静止过滤、事件状态机），全部 FFMPEG/OpenCV 调用走 `app/utils/ffmpeg.py` 封装约定；
- `backend/app/models.py` 增加 `RallySlice` / `BallEvent` 结构化结果；
- highlight 节点改造为「CV 切片 → 抽帧 → LLM 复核」两级，prompts/ 增加回合事件上下文注入模板；
- 评估脚本 `backend/evals/`（不进 pytest 单测，独立 CLI），输出 JSON 指标报告落 `backend/outputs/`；
- 各节点结果按全链路契约同步落库（`app/core.py` 约定）。

## 四、验收标准

1. 评估报告覆盖 E1–E5 全部实验，含 G1–G6 全指标数值与 Pass/Fail 判定；
2. G2 死球误入率 = 0（多球干扰排除为训练场景硬需求，未达成则 E2/E3 判 Fail）；
3. G4 回合切分：完整召回 ≥ 0.90，起止误差 ≤ 1s 的回合占比 ≥ 0.90；
4. G5 融合：准确率 ≥ 0.90（对齐 01 方案验收指标），LLM token 较 R1 下降 ≥ 50%；
5. G6 工程：1–5 分钟视频 CV 前置处理 ≤ 30s（不含 LLM 推理网络延迟），CPU 峰值内存 ≤ 4GB；
6. Mock 模式下 E3 可自动降级为纯 CV 结果且不崩溃（对齐 AGENTS.md「连续 100 条批量无崩溃」）。

## 五、风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| 自有训练素材不足，多球/暗光子集 < 10 条 | G2 评估不置信 | 先按 D2 公开数据 + 合成遮挡增强训练；补采素材前 E2 结论标注「低置信」 |
| 720p 小目标球检测 AP 不达 0.80 | G1 拖垮 G4 | 上 SAHI 切片推理 + YOLOv8s/v10n 加权框融合（公开参照 0.863 方案） |
| 手机镜头畸变使透视 H 失效 | 球径约束误杀真球 | 标定阶段加径向畸变补偿（`cv2.undistort`），畸变参数随视频缓存 |
| 状态机阈值（静止 1.5s / Δv 阈值）过拟合单一场地 | 跨场地泛化差 | 阈值做成 config.yaml 可配项，评测集覆盖 ≥ 2 种场地（硬地/红土） |
| LLM 复核 token 未达 50% 下降 | G5 经济性不成立 | 抽帧密度自适应：长回合降采样、事件帧必采 |
| Mock 模式评估与真实模型偏差大 | 决策误导 | Mock 仅验证稳定性，G5 增益判定以真实 Step 3.7 Flash 结果为准 |
