## 一、背景与目标

### 问题
高光阶段 `app/services/highlight.py::find_highlights` 当前把视频抽帧直接发给 LLM，由模型输出起止时间戳。实测存在**时间戳凭空臆造**的结构性缺陷：

- `app/utils/llm.py` 的 `_video_to_image_frames` 原本把 12 张**无时间戳**的裸帧发给模型，`prompts/highlight_analysis.py` 的 prompt 只告知总时长，模型无法把"看到 ACE"映射到真实秒数 → 返回的 `start/end` 是猜的。
- 由此出现"永远从 0 开始排"现象：日志中 `b0e6efe4bcd7` → `0–5 other / 5–10 ace`；`f8b5f9687e53` → `0–10 other / 10–20 ace`，清一色从视频开头排起。

### 已落地的关联修复（方案 1，见 `llm.py`）
在评估本方案前，已先行修复"模型无时钟"的输入问题：
1. 每帧注入真实时间戳标注（`[第 N 帧 @ t.s]`），并明确告知模型"依据帧时间戳给准确秒数，不要臆造"；
2. 采样密度 12 → 30 帧（最小步长 1s）；
3. DEBUG 日志打印 `帧时间戳=[...]`（依赖 [02-后端 loguru 日志 TDD 方案](./02-后端loguru日志TDD方案.md) 的 DEBUG 观测能力）。

方案 1 解决了"输入无时钟"，但仍有两块结构性短板：
- **均匀全片采样**：对 300s 预处理视频仍约 10s/帧，落在两帧之间的 5s ACE 只能估计；
- **定位职责仍在模型**：时间锚点本质由模型"据帧回推"，而非信号精确定位。

### 目标
- 把"何时发生"（精确到秒）从 LLM 职责剥离，交由 **ffmpeg 信号**完成；
- LLM 只负责"发生了什么"（ace/rally/winner/smash 语义判别）与候选窗口内的边界精修；
- 在**持平或更低** LLM token 成本下显著提升时间戳准确度，并结构性消除"从 0 开始"假象。

### 适用范围
pipeline 高光阶段，影响 `Segment` 时间戳来源与高光 prompt；涉及 `app/services/highlight.py`、`app/utils/llm.py`、`app/utils/ffmpeg.py`、`app/config.py`、`prompts/highlight_analysis.py`。

## 二、方案设计

### 2.1 总体架构（两阶段）
```
[preprocessing] → [Stage A: 候选定位 (ffmpeg 信号)] → [Stage B: LLM 段内精修] → [clamp/校验] → segments
```
`find_highlights` 调用顺序改为：先 `detect_candidates(...)` 得到候选窗口 → 再构造 prompt（携带候选窗口时间戳）→ 调用 `llm.complete_structured`。

### 2.2 Stage A — ffmpeg 候选定位（新增 `app/services/event_detect.py`）
两种互补信号取并集：

1. **场景切换（原生、零成本）**
   ```bash
   ffmpeg -i <video> -vf "select='gt(scene,SCENE_THRESH)',showinfo" -f null -
   ```
   解析 stdout 中 `pts_time` 得到镜头边界时间戳，捕捉"换点 / 机位移动 / 回放插入"等切变（`ffmpeg.run` 已返回 stdout，见 `app/utils/ffmpeg.py:26-41`）。

2. **运动强度（ffmpeg 抽帧 + numpy 帧差）**
   - ffmpeg 以 `MOTION_FPS`（默认 4）抽帧到临时目录；
   - 用 numpy（已确认 **2.4.6** 可用）读灰度帧，逐帧与上一帧算亮度 MAE，得活动强度序列；
   - 滑动均值平滑 → 阈值 `MOTION_THRESH` → 连续活跃窗口；
   - 专抓"稳镜头下的真实回合 / ACE"，是场景切换补不到的部分。

3. **合并与排序**：场景边界附近窗口 ∪ 运动窗口 → 按峰值活动降序 → 取 top-N（`CANDIDATE_TOP_N`，默认 5，且 ≤ `max_segments`）→ 输出带真实时间戳的候选段（`Segment`，`label="candidate"`）。

### 2.3 Stage B — LLM 段内精修（改造 `find_highlights` + prompt）
- **抽帧改为段内抽帧**：只在每个候选窗口内各抽 2–3 帧（沿用方案 1 的帧时间戳标注），而非全片均匀 30 帧；帧数 ≈ `CANDIDATE_TOP_N × 3`，与现状持平或更省。
- **prompt 改造**（`prompts/highlight_analysis.py::build_highlight_prompt`）：
  > 以下是带真实时间戳的候选窗口与段内帧，请判断每段是否为高光（ace/rally/winner/smash 或忽略），并**在候选窗口 ±2s 内**精修起止时间戳。
- **解析后 clamp**：返回段的起止必须落在对应候选窗口 ±2s 内，越界则拉回，确保时间戳始终由信号锚定。

### 2.4 配置与模型扩展（`app/config.py`）
`HighlightConfig`（`config.py:84-87`）新增旋钮：
- `scene_threshold: float = 0.4` — 场景切换判定阈值
- `motion_fps: int = 4` — 运动强度抽帧率
- `motion_threshold: float = 0.05` — 运动活跃阈值（示例值，待测试片标定）
- `candidate_top_n: int = 5` — 候选窗口上限

`Segment` 模型（`models.py:11-16`）无需改动，复用 `label` / `confidence` 字段。

### 2.5 兼容性
- **mock 模式**：`event_detect` 在 mock 下直接返回基于时长的候选段（沿用/改造现有 `mock_highlights`），保证链路与现有 73 测试不破。
- **无 ffmpeg / 无 numpy 降级**：回退到方案 1 全片带时间戳采样行为，不阻断主流程。

## 四、验收标准

- 候选窗口时间戳由 ffmpeg 算出，断言其与真实运动段重叠率 ≥ 80%（测试片）；
- 对真实网球视频，LLM 返回段不再系统性从 0 开始（人工抽看 3 条，ace/rally 时间戳落在合理回合内）；
- LLM 调用帧数 ≤ 现状（30 帧），token 成本持平或下降；
- 全量 `pytest` 通过、`check_logging.py` 通过、mock 模式链路可跑通。

## 五、风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| 场景 / 运动阈值需调参 | 漏检 / 误检 | 新增 config 旋钮，默认保守；用测试片标定 |
| 比分牌 / 观众席 / 回放插入造成运动误检 | 候选含非高光 | 要求活跃窗口 ≥ `min_segment_seconds`，LLM 过滤非高光 |
| 模型无视候选自由编时间 | 时间戳失真 | prompt 强约束"候选 ±2s 内"，解析后 clamp 回窗口 |
| 微妙高光（轻吊球）运动低 | 漏检 | 取 top-N 按活动排序 + LLM 语义兜底 |
| numpy / ffmpeg 不可用 | 功能降级 | 回退方案 1 全片带时间戳采样 |
