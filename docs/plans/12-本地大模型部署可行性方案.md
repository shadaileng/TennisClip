## 一、背景与目标

### 1.1 背景

TennisClip AI 当前使用阶跃星辰 Step 3.7 Flash 作为多模态理解模型，通过 OpenAI 兼容协议调用云端 API。项目面临以下潜在需求：

1. **离线部署**：部分用户（俱乐部、训练基地）网络受限，需本地运行
2. **成本控制**：云端 API 按 token 计费，高频使用成本较高
3. **隐私合规**：比赛/训练视频可能涉及隐私，用户不愿上传云端
4. **领域精度**：通用大模型缺乏网球深层视觉理解，分析质量有提升空间

### 1.2 目标

- 评估本地部署大模型的技术可行性与资源需求
- 调研网球领域现有开源方案与学术成果
- 设计渐进式技术演进路径（Prompt 深化 → CV 感知层 → 专有模型微调）
- **各阶段产物统一以工作流节点方式实现**：新能力注册为可编排节点，复用现有 DAG 执行器（`app/workflow/`），通过连线自由组合、启停开关，实现最灵活的改进方式
- 为后续实施提供决策依据

### 1.3 现有架构约束

| 组件 | 现状 | 约束 |
|------|------|------|
| LLM 客户端 | `openai>=1.0` SDK，`OpenAI()` 客户端 | 仅需 OpenAI 兼容端点 |
| 媒体输入策略 | `frame`（抽帧 base64）/ `video`（MP4 base64） | 本地模型需支持 Vision |
| 输出解析 | `_extract_json()` 从文本提取 JSON | 模型需稳定输出 JSON |
| 配置系统 | `config.yaml` providers 模式 + DB 运行时切换 | 已预置 ollama/vllm |
| Prompt 知识库 | `prompts/highlight_analysis.py`（~140 行） | 网球领域知识注入点 |
| **工作流系统** | `app/workflow/`：9 个内置节点 + `spec.py` 契约 + `graph.py` R1~R10 校验 | **本方案所有产物的承载方式**，新节点按 `@register` 注册即可上画布 |

## 二、本地部署可行性分析

### 2.1 代码层：零改动即可接入

项目已原生支持 OpenAI 兼容协议，本地模型接入**无需任何代码改动**：

```yaml
# config.yaml 已预置
- name: ollama
  base_url: http://127.0.0.1:11434/v1
  api_key_env: OLLAMA_API_KEY
  model: step3.7-flash  # 改为实际本地模型名

- name: vllm
  base_url: http://127.0.0.1:8000/v1
  api_key_env: VLLM_API_KEY
  model: step3.7-flash  # 改为实际本地模型名
```

接入步骤：

1. 启动本地推理服务（Ollama / vLLM / llama.cpp server）
2. 修改 `config.yaml` 中对应 provider 的 `model` 字段
3. 前端「模型管理」启用对应服务商，或设置 `ai.provider = ollama`
4. 设置 `mock_mode = never` 强制真实调用

### 2.2 适配要点

#### 2.2.1 视觉理解能力（核心瓶颈）

TennisClip 的高光识别依赖多模态视觉理解——给模型发送视频帧或整段视频，让模型判断高光时刻。

| 输入策略 | 格式 | 本地模型要求 |
|---------|------|------------|
| `frame`（抽帧） | `image_url` base64 JPEG 多图 | 需支持 **Vision**（多模态图像输入） |
| `video`（视频直送） | `video_url` base64 MP4 | 需支持**视频理解**（极少本地模型支持） |

**结论**：本地部署建议固定使用 `frame` 策略，`video` 策略暂不可用。

#### 2.2.2 JSON 结构化输出

`llm.py` 的 `_extract_json()` 从模型输出中提取 JSON（容忍 markdown 代码块包裹）。本地模型需：

- 能稳定输出 JSON 格式
- 理解网球领域术语（ace、rally、winner 等）

建议：在 system prompt 中进一步强化 JSON 格式约束，或使用支持 function calling / structured output 的模型。

#### 2.2.3 StepFun 专有参数兼容

`llm.py` 第 269-273 行传递了 `enable_thinking` 和 `reasoning_effort` 两个 StepFun 专有参数。本地模型会忽略这些 `extra_body` 字段（OpenAI SDK 允许），**不会报错**，但不会有推理增强效果。

### 2.3 硬件资源需求

| 模型 | 参数量 | 量化 | VRAM 需求 | 推理速度（估） | 适用场景 |
|------|--------|------|-----------|--------------|---------|
| Qwen2.5-VL-7B | 7B | Q4_K_M | ~6GB | 15-30s/次 | 入门级 GPU / 高端 CPU |
| Qwen2.5-VL-7B | 7B | FP16 | ~16GB | 5-15s/次 | RTX 3060 12GB+ |
| Qwen2.5-VL-32B | 32B | Q4_K_M | ~20GB | 30-60s/次 | RTX 4090 24GB |
| Qwen2.5-VL-72B | 72B | Q4_K_M | ~40GB | 60-120s/次 | A100 80GB |
| InternVL2-8B | 8B | Q4_K_M | ~6GB | 15-30s/次 | 入门级 GPU |
| LLaVA-1.6-7B | 7B | Q4_K_M | ~6GB | 15-30s/次 | 入门级 GPU |

> **注意**：项目验收指标要求 1-5 分钟视频端到端 ≤ 30s（不含模型推理网络延迟），本地推理 7B 模型可能接近该上限。

### 2.4 各推理框架对比

| 框架 | 优势 | 劣势 | 与 TennisClip 兼容性 |
|------|------|------|---------------------|
| **Ollama** | 一键安装、自动量化、OpenAI 兼容 API | 性能优化有限、大模型支持滞后 | ✅ 完美（config.yaml 已预置） |
| **vLLM** | 高吞吐、PagedAttention、连续批处理 | 配置复杂、GPU 要求高 | ✅ 完美（config.yaml 已预置） |
| **llama.cpp** | CPU 推理友好、GGUF 量化丰富 | 多模态支持需额外配置 | ✅ 兼容（启动 OpenAI 兼容端口） |
| **SGLang** | 高性能、结构化输出优化 | 社区较小、文档较少 | ✅ 兼容 |
| **LocalAI** | 多模型支持、插件丰富 | 项目活跃度下降 | ✅ 兼容 |

## 四、技术路径规划（工作流节点化）

> **核心原则**：三个阶段的**所有产物统一注册为可编排工作流节点**，复用现有 DAG 执行器（`app/workflow/` 的 `spec.py` 注册表 + `graph.py` 校验 + `executor.py` 执行）。
> 每个新节点遵循统一契约：`@register(NodeSpec(...))` 装饰、签名 `run(ctx, params) -> dict[port, value]`、薄封装 services 层、节点是 services 的薄封装不重复业务逻辑。
> 带来的灵活性：
> - **自由组合**：新旧节点在 SVG 画布上任意连线，同一视频可并行跑「旧信号检测」与「新 CV 检测」对比
> - **渐进启用**：每个节点带 `enabled` 开关，验证通过后再启用，失败可单点停用回退
> - **参数化调优**：阈值、模型、知识库档位等全部走 `ParamSpec` 驱动的前端表单，无需改代码
> - **旧管线零回归**：现有 9 个内置节点行为不变，新节点并存，`compile_from_legacy` 编译的默认图不受影响

### 4.1 路径总览与节点映射

```
阶段 1（立刻可做）          阶段 2（1-2 月）              阶段 3（3-6 月）
Prompt 工程深化         →    传统 CV 感知层接入        →    开源 VLM 微调
零成本、零基础设施           中等成本、高性价比            高成本、最高质量
   ↓                            ↓                            ↓
analyze.highlight       新增 detect.* 节点族           analyze.highlight
report.technical        （6 个检测节点）               model 参数切换
参数扩展 / 知识库注入          post.score_highlights          （微调权重注册为
                          post.classify_strokes             provider，节点不变）
```

| 阶段 | 产物形态 | 节点类型（type） | 说明 |
|------|---------|-----------------|------|
| **阶段 1** | 既有节点参数扩展 + 内部知识库注入 | `analyze.highlight`（增强）、`report.technical`（增强） | 不新增节点，扩展 ParamSpec + Prompt 知识库；作为阶段 2/3 的节点基础 |
| **阶段 2** | **6 个新节点**（4 detect + 2 post） | `detect.tracknet` / `detect.court` / `detect.player` / `detect.pose` / `post.score_highlights` / `post.classify_strokes` | CV 感知层全部节点化，可与旧 `detect.candidates` 并联对比 |
| **阶段 3** | 既有节点模型参数切换 | `analyze.highlight` 的 `model` 参数 | 微调 VLM 注册为 provider，节点零改动 |

### 4.2 阶段 1：Prompt 工程深化（既有节点增强）

**目标**：不改动节点图结构，在既有两个 LLM 节点内部注入更丰富的网球领域知识。

**节点级改动**（不新增节点，仅扩展 `ParamSpec` 与 Prompt 构建）：

| 节点 | 改动内容 | 新增参数（ParamSpec） | 工作量 |
|------|---------|----------------------|--------|
| `analyze.highlight` | 增强视觉判别规则 + few-shot 示例 | `prompt_variant`（select：standard/strict/teaching），可切换严格度 | 1 周 |
| `report.technical` | 教学知识库 3 条/级 → 20+ 条/级 | `knowledge_level`（select：basic/standard/expert），知识库深度档位 | 1-2 周 |
| （内部模块） | 新增 `prompts/tennis_domain.py` 网球规则 + 生物力学知识库 | 无（被上述节点内部引用） | 1-2 周 |
| （评估） | 10-20 段标注视频评估数据集 | 无 | 1 周 |

**改动文件**：

```
backend/prompts/
├── highlight_analysis.py    # 修改：增强视觉判别规则 + build_highlight_prompt 增加变体
├── report_templates.py      # 修改：扩展教学知识库（TEACHING_KNOWLEDGE → 分档）
└── tennis_domain.py         # 新增：网球规则/生物力学知识库（纯数据模块）

backend/app/workflow/nodes/
├── analyze_highlight.py     # 修改：新增 prompt_variant ParamSpec 并透传
└── report_technical.py      # 修改：新增 knowledge_level ParamSpec 并透传
```

**灵活性体现**：用户可在画布上对同一 `analyze.highlight` 节点配置不同 `prompt_variant`，并联两条分支对比严格/宽松模式的识别结果，无需改代码。

### 4.3 阶段 2：CV 感知层接入（6 个新节点）

**目标**：把 TrackNet、球场检测、球员检测、姿态估计、高光评分、击球分类封装为 6 个新节点，与既有 `detect.candidates` 并存，用户在画布上自由选择或并联对比。

#### 4.3.1 需要扩展的端口类型

现有 `PortType` 只有 5 种（`video / duration / candidates / highlight / report`），新增 CV 节点需要 3 种新端口类型：

```python
# app/workflow/spec.py 的 PortType 新增
class PortType:
    ...
    TRACK = "track"    # 球轨迹点列表（TrackNet 输出）
    COURT = "court"    # 球场关键点/坐标系
    POSE = "pose"      # 姿态关键点序列
```

#### 4.3.2 新节点规格一览

| # | 节点类型（type） | 标签 | category | stage | expensive | 输入端口 | 输出端口 |
|---|-----------------|------|----------|-------|-----------|---------|---------|
| 1 | `detect.tracknet` | TrackNet 球追踪 | detect | detecting | 否（GPU 轻量） | video, duration | track, candidates |
| 2 | `detect.court` | 球场关键点检测 | detect | detecting | 否 | video | court |
| 3 | `detect.player` | 球员检测追踪 | detect | detecting | 否 | video, duration | candidates |
| 4 | `detect.pose` | 姿态估计 | detect | detecting | 否 | video | pose |
| 5 | `post.score_highlights` | 高光评分排序 | post | postprocessing | 否 | candidates, video | highlight |
| 6 | `post.classify_strokes` | 击球类型分类 | post | postprocessing | 否 | highlight, pose | highlight |

> **双输出设计说明**：`detect.tracknet` 同时输出 `track`（原始轨迹）与 `candidates`（轨迹聚合成的候选窗口），既能给下游 `analyze.highlight` 供候选，也能给可视化/统计节点供轨迹点——一个节点多种用法，是灵活性的关键。

#### 4.3.3 各节点详细规格

**① `detect.tracknet` — TrackNet 球追踪**

```python
@register(NodeSpec(
    type="detect.tracknet",
    label="TrackNet 球追踪",
    category="detect",
    description="TrackNet 深度网络追踪网球轨迹，聚合为候选窗口（替换/对比 ffmpeg 音频信号）",
    inputs=[
        Port(name="video", type=PortType.VIDEO),
        Port(name="duration", type=PortType.DURATION),
    ],
    outputs=[
        Port(name="track", type=PortType.TRACK),        # 原始轨迹点
        Port(name="candidates", type=PortType.CANDIDATES),  # 聚合候选窗口
    ],
    params=[
        ParamSpec(key="confidence", label="置信度阈值", type="float", default=0.5,
                  min=0.0, max=1.0, description="低于此置信度的球位置丢弃"),
        ParamSpec(key="cluster_gap", label="聚类间隔", type="float", default=4.0,
                  min=0.5, max=15.0, description="相邻击球聚为回合的间隔上限（秒）"),
        ParamSpec(key="top_n", label="候选上限", type="int", default=5,
```

### 4.6 前置：工作流节点独立性加固（Step 0）

> 现有 9 个内置节点是**"契约独立、运行时共享"**的轻量编排——数据流经端口解耦，但运行时存在 5 类耦合。新增 6 个 CV 节点若直接叠加会继承全部旧耦合（尤其依赖 GPU 的节点更易失败、并联分支共享 highlight 有污染风险），故须先加固再扩节点。

#### 4.6.1 现状：5 类耦合点

| # | 耦合类型 | 证据 | 影响 |
|---|---------|------|------|
| 1 | **全局注册表** | `spec.py:66-67` 模块级 `_SPEC_REGISTRY`；`nodes/__init__.py` 需手动 import 每个节点模块 | 新增节点必须改清单；类型名重复抛错（`spec.py:93`） |
| 2 | **串行拓扑 + 失败传播** | `executor.py:100` Kahn 序串行执行；`:129-136` 非 `optional` 节点失败 → 任务 FAILED | 仅 `report.technical` 为 `optional=True`，其余任一节点失败即全盘失败，无失败隔离 |
| 3 | **共享可变状态** | 全节点共享同一 `Context`（config/task_out/result）；`detect_candidates.py:48-60`、`preprocess_transcode.py:46-52` 用 try/finally **临时改写共享 config 再恢复** | 串行下侥幸安全，一旦并行即竞态 |
| 4 | **引用传递 + 副作用** | `edit_concat.py:51-53` **原地修改上游传入的 `highlight`**；3 个节点内部直调 `db_service` 落库 | 并联分支共享同一 highlight 时互相污染（4.5 示例 B 的直接风险） |
| 5 | **端口类型仅校验字符串名** | R4 只比对端口类型字符串，不校验运行时值的 Python 实际类型 | 传错对象到节点深处才炸，新 TRACK/COURT/POSE 端口同样裸奔 |

**隐式耦合**：`executor.py:140-146` 兜底投影会扫描**所有节点输出**找 `highlight` 补写 `result` —— 任何节点输出端口叫此名都可能被误采。

#### 4.6.2 加固设计：三个批次

**批次 A（P0，1-2 天）：状态与数据隔离**

| 项 | 改动 | 设计 |
|----|------|------|
| A1 config 隔离 | `executor.py` 主循环每节点前 `ctx.config = copy.deepcopy(self.config)` | AppConfig 纯 dataclass，深拷贝微秒级；节点内改 config 天然隔离，try/finally 恢复反模式可删。**并行执行的硬前提** |
| A2 函数式传值 | `edit_concat.py` 等改 `highlight.model_copy(update={...})` 生成新对象 | 禁止原地改端口值；Pydantic 原生支持零成本；防并联分支污染 |
| A3 运行时类型校验 | `spec.py` 新增 `PORT_PY_TYPES` 映射 + `validate_port_value()`，执行器在 `store()` / `resolve_inputs()` 双向校验 | 端口类型从"约定"升级为"强制"；新 TRACK/COURT/POSE 注册即纳入校验 |
| A4 自动注册 | `nodes/__init__.py` 改 `pkgutil.iter_modules` 自动发现导入 | 新节点放文件即注册，Step 2.9 的 6 个手动 import 归零 |

```python
# A1: executor.py 主循环
ctx.config = copy.deepcopy(self.config)   # 节点级隔离
ctx.inputs = ctx.resolve_inputs(self.graph, node_id)

# A3: spec.py
PORT_PY_TYPES: dict[str, tuple] = {
    "video": (Path,), "duration": (int, float),
    "highlight": (HighlightResult,), "report": (TechnicalReport,),
    "candidates": (list,), "track": (list,), "court": (dict,), "pose": (dict,),
}
```

**批次 B（P1，3-5 天）：失败隔离**

| 项 | 改动 | 设计 |
|----|------|------|
| B1 失败策略参数化 | `NodeSpec` 增 `on_failure: str = "fail"`（`fail` \| `skip`，默认 fail 向后兼容） | 执行器级联跳过：`skip` 节点抛错 → 标记 skipped → 下游必填输入缺失时**自动 skipped 而非 raise**。CV 节点标 `skip`：TrackNet 挂掉退回无候选模式（`analyze.highlight` 的 candidates 本就 `required=False`，下游走均匀切片兜底），**任务仍 SUCCEEDED** |
| B2 去掉隐式兜底 | 删除 `executor.py:140-146` 输出扫描 | 改为 `validate()` 期检查 `output.artifact` 的 highlight 入边，缺连在草稿校验（`POST /workflows/validate`）提示；执行期只信显式连线 |

**批次 C（P2，~1 周，需批次 A 完成）：并行与副作用解耦**

| 项 | 改动 | 设计 |
|----|------|------|
| C1 同层并行 | `graph.py` 新增 `topo_levels()`（Kahn 分层）；执行器同层节点 ThreadPool 并发 | 典型收益：`detect.tracknet` ∥ `detect.court` ∥ `detect.pose` 并发，示例 B 感知阶段耗时 ≈ 最慢单节点而非三者之和。**前置：A1+A2**；风险：SQLite 多线程写需核查 `db_service` 会话管理 |
| C2 落库解耦 | 节点内部 `db_service` 直调改为 `NodeSpec.persists=[("video","highlight_video")]` 声明式，执行器统一落库 | 节点变纯函数，可测性大幅提升；同层保持 node.id 升序确保日志可复现 |

#### 4.6.3 优先级与工作量

| 批次 | 解决耦合 | 工作量 | 风险 | 排期 |
|------|---------|--------|------|------|
| **A（P0）** | 1/3/4/5 | 1-2 天 | 低（deepcopy 需确认无可拷贝字段；90+ 测试回归） | **Step 0，必须先于 Step 2** |
| **B（P1）** | 2 + 隐式投影 | 3-5 天 | 中（跳过语义需全测试矩阵覆盖） | **Step 0，与 A 同批** |
| **C（P2）** | 串行性能 + 副作用 | ~1 周 | 中（SQLite 线程安全、并发确定性） | 与 Step 2 并行推进 |

**测试策略**：每批次先补测试再改代码 —— A 加「节点改 config 不影响其他节点」「highlight 分支互不污染」；B 加「TrackNet 失败 → 全链 skipped 而非 FAILED」；C 加「同层并发结果与串行完全一致」。

## 八、风险与应对

| 风险 | 影响 | 概率 | 应对方案 |
|------|------|------|---------|
| 本地模型视觉理解不足 | 高光识别准确率大幅下降 | 中 | 阶段 1/2 先行验证，CV 感知层补偿；节点 `model` 参数一键切回云端 |
| GPU 显存不足 | 无法运行 7B+ 模型 | 中 | 量化（Q4_K_M）降显存；或用 Ollama 自动优化 |
| 训练数据标注成本高 | 阶段 3 延期 | 高 | 用阶段 1/2 的 LLM 输出作为伪标签，半自动标注 |
| TrackNet 在非广播视频上精度下降 | 球追踪失效 | 中 | 节点 `enabled=false` 单点停用，回退旧 `detect.candidates` 分支 |
| 本地推理延迟超标 | 不满足 30s 验收指标 | 中 | 减少抽帧数（max_frames=8）；用更小模型（3B） |
| Ollama/vLLM 版本兼容性 | OpenAI API 不兼容 | 低 | 项目已用标准 OpenAI SDK，兼容性风险极低 |
| **端口类型扩展破坏旧图** | 已保存的 9 节点工作流图校验失败 | 低 | 新增 `PortType` 是**纯增量**（不改既有 5 种），旧图端口类型不变 |
| **新节点参数校验失败（R10）** | 图校验报错无法保存 | 中 | `ParamSpec` 设置合理 default/min/max；`resolve_params` 单测覆盖边界 |
| **CV 依赖冲突** | torch/ultralytics 引入版本冲突 | 中 | 作为 `[project.optional-dependencies]` 可选 extras，不装不影响基础功能 |
| **新节点拖慢执行** | CV 推理耗时导致任务超时 | 中 | 节点 `expensive` 标记 + `frame_stride`/`interval` 参数降载 + `enabled` 停用 |
| **图复杂度上升** | 用户编排出非法/低效图 | 低 | R1~R10 校验兜底 + `POST /validate` 草稿校验 + 内置预置图模板 |
| **config 深拷贝隐藏不可拷贝字段** | 批次 A1 执行器每节点 deepcopy 抛错，任务全部失败 | 低 | 启动时冒烟自检 + `AppConfig` 纯 dataclass 约束写入注释；异常时降级为浅拷贝并 `logger.warning` |
| **级联跳过语义误伤** | 应失败的任务被静默跳过，产出空结果却显示成功 | 中 | 仅 `on_failure=skip` 节点生效（默认 `fail` 不变）；skipped 数量与节点清单写入 `TaskResult` 供前端展示 |

## 九、决策建议

### 9.1 立刻可做（零成本）

- ✅ 扩展 Prompt 知识库 + 既有节点参数化（阶段 1，不新增节点）
- ✅ 端口类型扩展 + 6 个 CV 节点注册（阶段 2，开源权重直接用，图上自由编排）
- ✅ Ollama + Qwen2.5-VL-7B 注册为 provider，画布 `model` 下拉切换验证

### 9.2 推荐优先级

```
P0（立刻）：阶段 1 既有节点参数化 + 阶段 2 端口扩展与 6 节点注册
P1（1-2 月）：节点单元测试 + 示例图端到端 + 本地 provider 注册验证
P2（3-6 月）：VLM 微调 + 注册 provider（节点零改动，视阶段 1/2 效果决定投入）
```

### 9.3 工作流节点化的灵活性收益（总结）

| 灵活性维度 | 传统改法 | 工作流节点改法 |
|-----------|---------|---------------|
| 启用新检测能力 | 改 `event_detect` 内部分支逻辑 | 画布新增 `detect.tracknet` 节点连线 |
| 新旧方案对比 | 改代码 + 重新部署 | 同图并联两条分支，分别输出对比 |
| 阈值/模型调参 | 改配置文件重启 | 节点表单 `ParamSpec` 实时调 |
| 单点回退 | 回滚代码 | 节点 `enabled=false` 停用 |
| 组合创新（如 CLIP 初筛 + LLM 精析） | 硬编码固定顺序 | 画布自由连线，拓扑排序执行 |
| 微调模型接入 | 改调用代码 | 注册 provider → `model` 下拉自动出现 |

### 9.4 不推荐

- ❌ 从零训练网球大模型（成本过高、数据不足）
- ❌ 直接用 video 策略对接本地模型（本地模型普遍不支持视频理解）
- ❌ 跳过 CV 感知层直接微调 VLM（缺乏结构化特征支撑）
- ❌ 把 CV 逻辑硬编码进 `event_detect` / `core.py`（应保持节点化，避免耦合、丢失编排灵活性）
