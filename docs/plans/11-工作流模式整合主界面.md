## 一、背景与目标

### 1.1 现状

当前前端存在两套交互模式：

| 模式 | 入口 | 体验 |
|------|------|------|
| **简易模式** | `UploadPanel`（主页面左列）+ `StrategyModal`（弹窗） | 直接上传视频 → 策略弹窗配置阶段/模式/层级 → 开始处理 |
| **工作流模式** | 头部「工作流」按钮 → `WorkflowCanvas`（全屏画布）或 `WorkflowPanel`（侧边弹窗） | 节点编排 → 保存/激活 → 上传视频按激活工作流执行 |

**问题**：

1. **功能重复**：简易模式的策略设置（阶段开关、分析模式、层级）与工作流模式的节点编排功能重叠
2. **入口分散**：头部 5 个独立按钮（模型管理、策略设置、工作流、历史任务），用户不知道该用哪个
3. **模式割裂**：两种模式的数据流和配置路径不统一，维护成本高
4. **工作流利用率低**：全屏画布/弹窗编辑器入口隐蔽，多数用户停留在简易模式

### 1.2 目标

- **去掉简易模式**：删除 `UploadPanel` 的策略概览区域和 `StrategyModal`
- **工作流全屏模态**：点击头部「工作流」按钮 → 打开 `WorkflowCanvas`（ComfyUI 风格 SVG 节点画布）全屏编辑
- **主页面左右等宽**：上传视频（左列）+ 任务处理（右列），两列等宽
- **头部精简**：Logo + 健康状态 + 模型管理 + 工作流 + 历史任务

## 三、数据流变更

### 3.1 策略配置路径

**变更前**：
```
用户 → StrategyModal → saveStrategy() → config KV (pipeline.stages / llm.analysis_mode / highlight.level)
                                        ↓
                              UploadPanel 读取展示
                                        ↓
                              submit() 时携带 level 参数
```

**变更后**：
```
用户 → WorkflowCanvas 编排节点 → saveDraft() → 工作流 API (POST /api/v1/workflows)
                                                 ↓
                                     activate() → 写入 config KV (workflow.default_graph_id)
                                                 ↓
                               UploadPanel 显示激活工作流名称
                                                 ↓
                               submit() 时后端自动使用激活工作流
```

### 3.2 关键原则

- 工作流激活/执行逻辑 **已在 09 号方案中实现**，本次主要改动前端 UI 布局
- 上传流程 **无需变更**：`submit()` 仍然走 `/api/v1/process`，后端根据激活工作流自动编译
- 服务商/模型选择 **保留**：仍通过配置 KV `ai.provider` / `ai.model` 控制

## 四、TaskCard 步骤条与工作流节点一一对应

### 4.1 现状问题

当前 TaskCard 步骤条**硬编码 4 个阶段**：

```
preprocessing → highlighting → editing → reporting
   预处理        高光识别       自动剪辑    报告生成
```

但工作流执行器按拓扑序执行各节点，每个节点上报独立的 `spec.stage`：

| 节点类型 | stage 值 | 节点标签 |
|---------|----------|---------|
| `input.video` | `input` | 视频输入 |
| `preprocess.transcode` | `preprocessing` | 预处理转码 |
| `detect.candidates` | `detecting` | 信号候选定位 |
| `analyze.highlight` | `highlighting` | LLM 高光识别 |
| `post.filter_segments` | `postprocessing` | 片段过滤 |
| `post.uniform_slices` | `postprocessing` | 均匀切片兜底 |
| `edit.concat` | `editing` | 剪辑合成 |
| `report.technical` | `reporting` | 技术分析报告 |
| `output.artifact` | `output` | 产物投影 |

**问题**：
1. TaskCard 只认 4 个 stage，`input`/`detecting`/`postprocessing`/`output` 会丢失
2. 用户自定义工作流可能跳过某些阶段（如不做报告），步骤条仍显示 4 个
3. 多节点同 stage（如两个 `postprocessing`），步骤条无法区分

### 4.2 方案设计：后端上报节点进度列表

#### 4.2.1 数据模型（`backend/app/models.py`）

新增 `WorkflowNodeProgress` 模型 + `TaskResult.workflow_nodes` 字段：

```python
class WorkflowNodeProgress(BaseModel):
    """单个工作流节点的执行进度。"""
    node_id: str          # 节点 ID（如 "n1"）
    node_type: str        # 节点类型（如 "analyze.highlight"）
    label: str            # 节点中文标签（如 "LLM 高光识别"）
    stage: str            # stage 上报值（如 "highlighting"）
    status: str = "pending"  # pending | running | done | failed | skipped
```

#### 4.2.2 执行器改动（`backend/app/workflow/executor.py`）

- 执行前按拓扑序初始化 `workflow_nodes` 列表（禁用节点标记 `skipped`）
- 执行每个节点时更新 `status`：`pending → running → done/failed`
- 终态时所有 `running` 节点标记 `done`

#### 4.2.3 前端 TaskCard 改动

- 从 `task.workflow_nodes` 读取动态节点列表渲染步骤条
- `workflow_nodes` 为空时回退到硬编码 4 阶段（旧任务兼容）

### 4.3 步骤条状态映射

| status | 视觉效果 | 说明 |
|--------|---------|------|
| `pending` | 灰色圆圈 + 编号 | 未开始 |
| `running` | 绿色脉冲圆圈 + ● | 当前执行中 |
| `done` | 绿色圆圈 + ✓ | 已完成 |
| `failed` | 红色圆圈 + ✕ | 执行失败 |
| `skipped` | 灰色虚线圆圈 + — | 节点已禁用 |

## 五、模型参数路由与任务查询修复

### 5.1 模型参数 `provider/model` 格式路由

**问题**：工作流画布中模型下拉选项为 `provider_name/model_id` 格式（如 `stepfun/step3.7-flash`），但 `llm.complete_structured` 的 `model_override` 只替换 model 名，不切换 base_url/api_key，导致用全局配置的服务商凭据调用错误的模型 API → 404。

**修复**：

| 文件 | 改动 |
|------|------|
| `spec.py` `_get_available_models()` | 返回 `provider_name/model_id` 格式（去重），供前端下拉显示 |
| `spec.py` `resolve_params()` | `model` 参数空 options 时动态填充 `_get_available_models()` 校验 |
| `llm.py` `complete_structured()` | `model_override` 含 `/` 时拆分 `provider_name` + `model_id`，通过 `get_provider_by_name()` 获取对应服务商的 base_url + api_key |

**模型参数传递链路**：

```
工作流画布选模型 → "stepfun/step3.7-flash"
        ↓
resolve_params 校验 → options 含该值 → 通过
        ↓
executor 传给 highlight_service → model="stepfun/step3.7-flash"
        ↓
llm.complete_structured → 拆分 "stepfun" + "step3.7-flash"
        ↓
get_provider_by_name("stepfun") → base_url + api_key
        ↓
用 stepfun 的凭据调用 step3.7-flash API → ✅
```

### 5.2 任务查询数据库 fallback

**问题**：`GET /api/v1/tasks/{task_id}` 只查内存队列（`TaskQueue._tasks`），任务完成后如果服务重启或队列清理，前端轮询返回 404 → 显示「任务不存在或已过期」。

**修复**：

```python
@app.get("/api/v1/tasks/{task_id}")
def get_task(task_id: str) -> dict:
    # 1) 优先内存队列（实时 stage/status 变化）
    try:
        return queue.get(task_id).model_dump()
    except KeyError:
        pass
    # 2) 兜底数据库（历史任务 / 队列已清理）
    detail = db_service.get_task_detail(task_id)
    if detail:
        return detail
    raise HTTPException(status_code=404, detail="task not found")
```

任务执行完后 `executor` 调用 `record_task_finish` 落库，即使内存队列丢失，前端轮询也能从数据库拿到结果。

### 5.3 候选人来源严格化

**问题**：`find_highlights` 在 `frame` 模式下总是内部跑 `event_detect.detect_candidates`，即使工作流中没有 `detect.candidates` 节点。导致无信号检测节点的工作流仍然在 prompt 中注入候选窗口。

**设计意图**：

| 场景 | 候选来源 | 说明 |
|------|---------|------|
| 工作流有 `detect.candidates` 节点 | 上游节点输出 | 通过连线传入 |
| 工作流无 `detect.candidates` 节点 | 无候选 | LLM 自由分析整段视频 |
| Legacy 管线（`core.py`） | 内部检测 | 保持向后兼容 |

**修复**：`find_highlights` 的 `candidates` 参数使用 `_NO_CANDIDATES` sentinel 区分三种情况：

```python
_NO_CANDIDATES = object()  # sentinel：调用方未传参（legacy 管线）

def find_highlights(..., candidates=_NO_CANDIDATES):
    if candidates is _NO_CANDIDATES:
        # legacy 管线：内部跑信号检测
        ...
    elif candidates:
        # 工作流上游节点传入了候选列表
        _final_cands = list(candidates)
    else:
        # candidates=None 或 []：无候选，不跑检测
        _final_cands = []
```

| 文件 | 改动 |
|------|------|
| `highlight.py` | `candidates` 默认值改为 `_NO_CANDIDATES` sentinel；三分支逻辑 |
| `analyze_highlight.py` | 传入 `candidates=candidates`（无上游连接时为 `None`） |

### 5.4 测试隔离：数据库引擎恢复

**问题**：`test_db_service_roundtrip` 用 `importlib.reload(db_service)` + `init_db(临时库)` 切换到测试数据库，测试结束后未恢复原始引擎。后续 upload 测试写入时指向错误的数据库 → `sqlite3.OperationalError: attempt to write a readonly database` → 500。

**修复**：`finally` 块中恢复原始引擎：

```python
finally:
    importlib.reload(db_service)
    db_service.init_db(load_config())  # 恢复指向原始 DB
```

## 八、风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|---------|
| 工作流面板数据加载 | 首次打开需请求 schema + workflows | App.vue `onMounted` 中预加载，打开模态时直接可用 |
| 策略配置迁移 | 用户习惯旧的策略弹窗 | 工作流节点画布提供更直观的编排体验 |
| `workflow_nodes` 字段大小 | 节点多时 JSON 响应变大 | 每节点仅 5 个字段，10 节点 < 1KB，可忽略 |
| 旧任务兼容 | 历史任务无 `workflow_nodes` | 前端空列表回退到硬编码 4 阶段，无需数据库迁移 |
| 小屏设备画布操作 | 全屏模态在小屏上节点拥挤 | 画布支持滚轮缩放（0.2x~3x）+ 拖拽平移 |
